# 2026-09-19 — Docker hardening pass

Audited the 3-container deploy (`postgres-db` / `mercon-api` / `mercon-frontend` via
`docker-compose.yml`, built by `.github/workflows/ci-cd.yml`). Conclusion: 3-service
split (db/api/frontend) already matches the app's actual boundaries — no case for
splitting further. Fixed concrete gaps instead:

1. **No resource limits** — one runaway container could starve the others on this
   VPS, which also runs unrelated non-Mercon containers (`mesiri-redis`,
   `mesiri-postgres` — see `docs/archive/incidents/dev-disk-enospc-forensic-report.md`).
   Added `mem_limit`/`cpus` to all three services in `docker-compose.yml`, each
   overridable via env (`POSTGRES_MEM_LIMIT`, `API_MEM_LIMIT`, `FRONTEND_MEM_LIMIT`,
   and matching `*_CPU_LIMIT`). Defaults: postgres 512m/1cpu, api 768m/1.5cpu,
   frontend 256m/0.5cpu — conservative guesses, tune once real usage is observed.
2. **API container ran as root** — `backend/api-server/Dockerfile` now runs as the
   built-in `node` user (uid 1000) instead of root. Verified nothing in the startup
   path (`CMD ["node", "dist/index.js"]`) needs root — no prestart migration/seed
   script runs inside the container (contrary to a stale comment in `ci-cd.yml`
   claiming a "prisma db push && seed" startup chain; that isn't wired up anywhere
   in `package.json` or `src/index.ts` as of this pass — not touched, just noting
   it for whoever looks next). `frontend/web-dashboard/Dockerfile`'s `nginx:alpine`
   stage was left as-is: the official image already runs its worker processes as
   the unprivileged `nginx` user by default; only the master process (which just
   binds port 80) stays root, which is normal for that image.
3. **Leaked secret** — `ci-cd.yml` had a hardcoded Gemini API key as a fallback
   (`secrets.GEMINI_API_KEY || 'AQ.Ab8...'`). Removed the fallback; `GEMINI_API_KEY`
   now comes only from the repo secret, empty-string default (feature already
   degrades gracefully when unset — see `docker-compose.yml` comment).
   **Action needed from the owner**: that key is in git history and must be treated
   as compromised — rotate/revoke it in Google AI Studio and set the new value as
   the `GEMINI_API_KEY` GitHub Actions secret.

### Follow-up (same day) — cpu-limit fix + health-check/backup phase

The `cpus` defaults above (api 1.5) broke the next dev deploy: the VPS only
has 1 CPU, and Docker hard-rejects any single service's `cpus` above the
host's actual core count. Fixed by lowering defaults to fit under that
ceiling (postgres 0.5, api 0.75, frontend 0.25 — `cpus` is a throttle, not a
reservation, so stacks can still safely oversubscribe it in aggregate).

That incident — a bad config value went unnoticed until someone read the raw
Action log — motivated a broader look at health-check/observability gaps.
Implemented as three phases (a fourth, opt-in alert-webhook phase, is
pending the owner picking a webhook target):

1. **Prod deploy now has a real health gate.** `ci-cd-dev.yml` already polled
   `docker inspect .State.Health.Status` for up to 60s post-deploy and curled
   `/health`, failing the job on either check — but `ci-cd.yml` (prod) just
   `sleep 8`'d and printed logs unconditionally, so a crash-looping container
   reported as a successful deploy. Ported dev's exact gate into `ci-cd.yml`
   (port 3050, project `mercon`).
2. **Frontend container had no healthcheck at all** — the only one of the
   three services missing one. Added `location = /healthz` to
   `frontend/web-dashboard/nginx.conf` (exact-match location, so it can't
   shadow the SPA catch-all or asset cache rules) and a matching
   `healthcheck:` block in `docker-compose.yml` using `wget` (nginx:alpine
   ships busybox wget, not curl).
3. **No automated database backups existed anywhere** — the only `pg_dump`
   usage in the repo was `sync-prod-from-dev.yml`'s one-off safety dump taken
   immediately before an overwrite. Added `.github/workflows/backup-db.yml`:
   nightly (`workflow_dispatch` too) `pg_dump` reusing that same proven
   command, written to `/var/backups/mercon` (deliberately not `/tmp`, which
   already holds the uploads mounts and has a prior ENOSPC history), 7-day
   local retention via `find -mtime +7 -delete`, plus an off-host copy via
   `actions/upload-artifact` (14-day retention) so a copy survives even if
   the VPS itself is lost. Restore is documented as a manual `pg_restore`
   procedure in the workflow's header comment, not automated — an untested
   automatic rollback path is its own risk.

### Not changed — flagged instead
- **Uploads bind mounts still live under host `/tmp`** (`/tmp/${CLIENT_NAME}-uploads`,
  `/tmp/uploads`). `/tmp` can be cleared on some distros' reboot policy, so this is a
  durability risk for uploaded documents. Not changed because moving it requires a
  one-time file copy on the VPS from the old path to a new persistent path (e.g.
  `/var/lib/mercon-uploads`) *before* the next deploy, or the app will appear to lose
  existing files (they'd still be on disk, just unmounted). No SSH access from here
  to do that migration safely. Path is already parameterized
  (`TMP_UPLOADS_DIR`/`CLIENT_NAME`), so once the owner migrates the data on the VPS,
  swapping the default in `docker-compose.yml` is a one-line change.
